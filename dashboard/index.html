About This Project

Purpose: This demonstration project showcases the capability to transform messy hospital data into FHIR-compliant format with comprehensive quality assurance.

Approach: Uses official German MII (Medizininformatik-Initiative) test data to demonstrate understanding of the German medical informatics ecosystem and interoperability standards.

Project Overview

This project demonstrates a complete ETL pipeline that transforms messy hospital data into HL7 FHIR R4 compliant resources, using official German MII test data from the Medizininformatik-Initiative.

"Reverse Engineering" Approach for Validation

Started with clean MII FHIR → Created messy CSV with realistic quality issues → Transformed back to clean FHIR → Validated against original gold standard

Phase 1 Extract & "Break" FHIR → Messy CSV
Phase 2 Transform & Clean CSV → Clean FHIR
Phase 3 Validate Compare to Gold Standard
Result Quality Dashboard Metrics & Visualizations

Data Quality Issues Handled

ID Formats P-001, PAT001, 00001 → PAT-00001
Date Formats DD.MM.YYYY, YYYY-MM-DD → ISO 8601
Gender Values M, male, männlich → standardized
Missing Data 10-15% nulls → handled gracefully
German Characters ä, ö, ü, ß → UTF-8 encoding
Reference Integrity Invalid IDs → logged & flagged
Tech Stack: Python • pandas • fhir.resources (FHIR R4) • pytest • JavaScript/CSS/HTML

How to Run This Project

Quick Start

# 1. Clone the repository git clone https://codeberg.org/YOUR-USERNAME/YOUR-REPO cd YOUR-REPO # 2. Install dependencies pip install -r requirements.txt # 3. Run the extraction (FHIR → CSV) python3 src/fhir_to_csv_extractor.py # 4. Run the transformation pipeline (CSV → FHIR) PYTHONPATH=. python3 src/pipeline.py # 5. Validate against original FHIR PYTHONPATH=. python3 src/validate_against_original.py # 6. View this dashboard open dashboard/index.html

Requirements: Python 3.9+, ~2GB disk space for test data
Execution time: ~2-3 minutes for full pipeline (200 patients)

🔄 Apache NiFi — Orchestration Layer

  • Visual pipeline design — no code for simple data flows
  • Automatic retry and configurable error handling
  • Real-time monitoring dashboard with back-pressure
  • Schedule-based execution (hourly, nightly, on-demand)
  • Built-in data provenance — full audit trail for compliance
Use case: Automatically ingest new FHIR bundles arriving each night from hospital source systems, validate structure, route errors to the data quality team, and forward clean data to Spark for transformation.

⚡ Apache Spark — Processing Layer

  • Parallel processing distributed across cluster nodes
  • In-memory computation for large-scale transformations
  • Fault tolerance — automatic recovery from node failures
  • Scales linearly with data volume (add nodes as hospital network grows)
  • Native Parquet/Delta Lake support for analytics
Use case: Process 200K+ patient records across a multi-site hospital network in minutes instead of hours, applying the same transformation logic demonstrated in this demo at production scale.

🏥 HAPI FHIR Server — Data Store

  • Full FHIR R4 REST API with search and validation
  • MII profile support (Kerndatensatz resources)
  • Terminology services (ICD-10-GM, LOINC, ATC lookups)
  • Subscription support for downstream consumers
  • Enterprise-grade persistence (PostgreSQL backend)
Use case: Serve as the central FHIR repository for the Data Integration Center, providing standards-compliant access for research platforms, clinical decision support, and cross-site queries within the MII consortium.

📊 Analytics Layer — Research & Reporting

  • Parquet files for efficient columnar analytics
  • Compatible with Spark SQL, Trino, and BI tools
  • OMOP CDM export for multi-site research studies
  • Data quality dashboards and trend monitoring
Use case: Enable researchers to run cohort queries across all integrated hospital data without impacting the FHIR server, supporting the MII Use Cases (POLAR, CORD, SMITH) with performant analytics.
